ZPD (最近发展区) 动态难度追踪 - 架构解析

改动逻辑说明与时序梳理 | ISSUE-03

涉及模块 (Affected Files)

  • backend/database.py: 扩展 course_progress 表结构，下沉 ZPD 状态（连对/连错/难度系数）的持久化。
  • backend/services/course_manager.py: 封装深模块 get_zpd_metrics 与 record_quiz_result，将状态演进计算完全隔离。
  • backend/services/slash_handler.py: 大模型交互网关。负责连接 ZPD 接口、向 LLM 注入 System Directive 并在流首抛出前端 prelude_hint 通知。

架构演进与深模块设计 (Deep Module Design)

Before: 静态出题 (Shallow Module)

过去，出题难度完全依赖模型每次根据上下文随机决定，存在严重的上下文遗忘与难度跳跃问题。系统在宏观视角上是“浅”的，无法记录和追踪用户受挫或顿悟的学习曲线。

After: ZPD 状态机 (Deepening)

通过数据库将“连对/连错”状态留痕，并以 0.1 步长计算出 0.5 ~ 3.0 的动态难度系数。业务逻辑像有限状态机一样，根据答题反馈自动升降级，并通过明确的“接缝 (Seam)”传入 LLM 的提示词管道。

架构级收益评估 (Benefits & Trade-offs)

高局部性与测试表面 (Locality & Test Surface):

难度的加减、封顶（3.0）与回退逻辑，全部收敛于深模块 course_manager.py 内，slash_handler.py 完全不关心数学逻辑，只负责粘合接口和拼装 Prompt，极大提高了代码内聚度和单元测试的纯净度。

零污染铁律实践 (Zero DB Pollution):

ZPD 指示和难度缩放控制（Prompt Directive）都在后端的动态渲染层按即用即抛（tail injection）生成，未写入 chat_messages 的历史表，杜绝了长期遗留噪声对记忆库的污染。
