系统架构盘点：深模块演进机会 (Deepening Opportunities)

基于现有的领域模型定义 (CONTEXT.md) 与当前代码库，我们通过**删除测试 (Deletion Test)** 扫描出了以下系统架构的“摩擦点 (Friction points)”，并提出了将这些**浅模块 (Shallow modules)** 演进重构为**深模块 (Deep modules)** 的方案。

1. 将 LLM 流式解析与工具执行逻辑解耦

LLM-Prompt-Injection 摩擦候选 (Candidate)
强力推荐 (Strong)

涉及文件: backend/services/agent_tools.py (AgentExecutor)

存在问题 (Problem)

AgentExecutor.run 是一个充当“上帝函数”的浅模块 (Shallow Module)。它严重混合了 LLM 流数据分块解析（提取 OpenAI 格式的工具调用）、工具执行的多线程调度以及系统状态管理。这严重缺乏局部性 (Locality)，因为哪怕仅仅是更换一个模型服务商或修改解析逻辑，都极易破坏底层的工具执行代码。二者之间毫无接缝 (Seam)可言。

解决方案与收益 (Solution & Benefits)

提取出一个 StreamParser 适配器（专门产出通用的解析事件流），并抽离一个完全独立的 ToolExecutionEngine 工具执行引擎。

收益：获得极高的杠杆率 (Leverage)。我们可以脱离具体的业务工具，单独为流式解析器编写测试。同时，工具执行引擎也蜕变成为一个深模块，对外提供清晰的接口 (Interface)，专注于并发工具的执行与结果回传。

2. 从底层网络路由中抽离角色 (Persona) 逻辑

LLM-Prompt-Injection 摩擦候选 (Candidate)
值得探索 (Worth exploring)

涉及文件: backend/services/model_router.py (stream_chat)

存在问题 (Problem)

stream_chat 函数通过硬编码一段长达 30 行的 perfect_one_shot 字符串直接篡改了对话历史记录。这导致核心的“人设 (Persona) 业务逻辑”发生了严重的缝隙泄漏，直接污染了网络路由模块。底层路由器根本不应该知道“Mei Wenfeng”的存在，也不该关心这 6 步思考法。

解决方案与收益 (Solution & Benefits)

将 One-Shot 的动态注入逻辑完全移动到 prompts.py 的 PromptBuilder 适配器中。路由器的接口 (Interface)设计应保持纯粹，只接收已经完全就绪的 messages 数组。

收益：大幅改善人设设计的局部性 (Locality)。以后哪怕对人设进行翻天覆地的修改，也无需碰触网络层代码。路由器将纯粹蜕变为一个深模块，只对 LiteLLM API 的网络稳定性负责。

3. 将巨石阵斜杠指令重构为“策略模式”

LLM-Prompt-Injection Sandbox-Evolving 摩擦候选 (Candidate)
强力推荐 (Strong)

涉及文件: backend/services/slash_handler.py

存在问题 (Problem)

slash_handler.py 内部为每一个斜杠指令硬塞了极其庞大的多行 XML 系统指令 (<system_directive>)。它将 HTTP 流响应生成、Prompt 文本拼接和核心指令业务逻辑完全搅和在了一起。这是一个典型的浅模块，且彻底违背了删除测试 (Deletion Test)：当你只想删除一个废弃指令时，你被迫要在一个数百行的巨型 if/elif 链条中痛苦定位，容易产生误伤。

解决方案与收益 (Solution & Benefits)

提取出一个通用的 CommandStrategy 接口 (Interface)。每一条指令都自成一个独立类（如 LessonCommand），并实现自己的 get_system_injection() 和执行逻辑。核心 Handler 退居幕后，只做路由注册。

收益：打造出一条非常清晰且易于扩展的接缝 (Seam)。极大提升局部性 (Locality)：一条指令等于一个独立的文件/类，修改互不干扰。

4. 将报文组装与尾部交叉引用重构为独立深模块 (ContextManager)

Context-Orchestration 摩擦候选 (Candidate)
强力推荐 (Strong)

涉及文件: backend/services/context_manager.py (新增), chat.py, slash_handler.py, model_router.py, agent_executor.py

存在问题 (Problem)

目前的报文组装分散在多个不同文件中：chat.py 拼接 RAG 与 IDE 状态；model_router.py 遍历历史注入 One-Shot；agent_executor.py 硬修改 messages[0] 塞入执行协议。这是一个严重散落的浅模块 (Shallow Module)群，缺乏局部性 (Locality)。根据删除测试 (Deletion Test)，删改任何一处都会破坏整体报文结构，二者间毫无接缝 (Seam)。此外，长对话中顶部规则被稀释，导致 9B 小模型严重遗忘动作星号与工具调用。

解决方案与收益 (Solution & Benefits)

构建统一的 ContextManager 深模块 (Deep Module) 作为唯一接口，提供 assemble_messages 统一收口 RAG 注入、One-Shot 规范与“三明治尾部注入（向最新 User 尾部注入带交叉引用指针的协议与时间戳）”。

收益：获得巨大的杠杆率 (Leverage)。复杂的上下文编排被封装在清晰的接缝 (Seam)之后。测试不再依赖网络与数据库路由，满足“接口即测试表面 (The interface is the test surface)”。尾部交叉引用指针充当了强大的注意力适配器 (Adapter)，确保小模型在 50+ 轮对话后仍能 100% 遵守规则。

优先行动建议 (Top Recommendation)

当前最迫切、回报率最高的行动是实施 候选方案 4：构建 ContextManager 深模块与三明治尾部注入！这是解决我们刚实测发现的 9B 模型遗忘动作星号和口嗨不调工具问题的唯一完美接缝 (Seam)。 其次，针对斜杠命令系统，建议逐步推进 候选方案 3（策略模式），彻底摆脱巨石阵代码。
