双层记忆主动召回漏斗与四类正交工具路由架构决策

承接并固化 PLAN-03（ISSUE-52 / ISSUE-53 / ISSUE-66 / ISSUE-67 / ISSUE-68）与 Bug #49 演进成果。将单层被动向量检索升级为“Layer 1 被动向量预召回 + Layer 2 SQLite 四阶原子漏斗主动探索”双层记忆架构，构建全量 12 工具的 [Memory]/[Workspace]/[Web]/[Collab] 四类正交路由表，放开多轮探索深度并打通可见性过滤、多词相关度排序与全链路工具标签清洗。

RAG-Vector-Indexed (Layer-1 预召回 + _memory_recall_pointer) Active-Memory-Funnel (Layer-2 四阶 [Memory] 漏斗) Orthogonal-Tool-Routing (四类正交工具路由) DB-Transaction (SQLite 只读查询与 rolled_back 过滤) Bug #49 (多词分词排序与 <tool_batch> 净化)
1

背景与技术挑战 (Context & Challenges)

被动检索盲区、工具分类混淆与小模型记忆检索偏航

挑战一：单一被动 RAG 的时间盲区与语境断层

原有记忆召回仅依赖 context_manager.py 在发包前静默注入 ChromaDB 切片（<retrieved_past_memory_archives>）与近期日记（<recent_journal_summaries>）。当用户追问“哪个月开始聊”、“某天发生了什么”或某条日记前的原始对话细节时，向量 Top-K 既无法给出日历全局分布，也无法按 session_id 还原前后对话上下文。

挑战二：复合 mode 参数与工具排列序诱发盲搜

初代自主检索仅设单一 search_memory(mode=...)，并将关键词搜索放在最前并附带总纲式描述。实际运行中端侧小模型频繁绕过日历总览、直接盲传多关键词短语触发精确子串 LIKE（任意一词不相邻即返回空，Bug #49），或混淆概念而误调用 grep_search / read_file 在磁盘目录翻找聊天记录。

挑战三：硬编码步数封顶与跨表视野遮蔽

原 AgentExecutor 硬编码 MAX_MEMORY_SEARCH_STEPS = 3 且默认传入 max_iterations=5，复杂考据流程（查日历 -> 看早期时间线 -> 搜词 -> 展开对话）尚未收敛即被强制阻断；此外，历史海量 journals 易遮蔽较晚开始的 conversations 分布，而只查单一 target 为空时也缺乏跨表与全库最早日期锚点提示。

挑战四：已回滚记忆残留与 <tool_batch> 脏标签泄漏

部分被撤回测试轮次写入的 memory_logs(status='rolled_back') 在 Chroma 已被清除，但 SQL 检索仍可搜出导致污染上下文；同时旧版对白与工具调用空壳（如 <tool_batch>...</tool_batch>）在压缩纪要、记忆衰减与检索预览中未被剥离，挤压有效正文预算。

决策方案与深模块解耦 (Decision & Solution)

双层协同、四阶原子漏斗、正交分类路由与 SQLite 深模块硬化

2.1 双层记忆架构与四原子 [Memory] 漏斗注册顺序

保留 Layer 1（ChromaDB 被动预召回） 作为零工具延迟首屏上下文，并在 <retrieved_past_memory_archives> 与 <recent_journal_summaries> 首行就地附加 _memory_recall_pointer 提示“仅为局部切片，缺细节时调用 [Memory] 工具”；Layer 2（MemorySearchEngine over SQLite） 在 TOOL_REGISTRY 中按从粗到细的严格漏斗顺序注册 4 个零 mode、单职责原子工具：

  1. get_memory_calendar（默认 15 天，上限 31 天）：按天聚合 memory_logs 日记条数与 chat_messages 会话段数/消息数及每日最多 4 个 chat_sessions.title，作为全史宏观测绘首站；
  2. get_memory_timeline（默认 5 条，上限 15 条）：按时间顺序列出清洗后的 ~150 字短摘要（PREVIEW_CHARS = 150）与记录 ID；
  3. search_memory（默认 5 条，上限 15 条）：按关键词定位具体日记或对话预览，工具描述显式引导宏观日期跨度先走 get_memory_calendar / get_memory_timeline；
  4. expand_memory（source_type + record_id，DEFAULT_CONTEXT_TURNS = 4，MAX_CONTEXT_TURNS = 8）：展开完整日记正文或同一 session_id 边界内前后对话窗口，绝不跨会话越界。

2.2 宏观时间尺度、双向锚点与三级渐进空日期引导

在 backend/services/memory_search_engine.py 的 _build_date_clauses 中，date_range 支持 'YYYY-MM-DD'、'YYYY-MM'、'YYYY'（如 '2026'）、'recent_7d'、'recent_30d' 与 'all'（省略所有日期参数即扫描全库），并辅以闭区间 start_date/end_date。calendar 与 timeline 同时支持 target（all / journals / conversations）与 order（newest / oldest）：发生截断时，返回头尾显式输出 earliest_active_day、total_active_days / total_matching 及可执行的下一步参数建议；查询落空时，_build_empty_notice 依次按“同月活跃日 -> 同年活跃月份 -> 全库活跃年份”渐进退回提示，_build_peer_target_hint 在单侧 target 为空而对侧有记录时客观提示切回 target='all' 或对侧类别（严格零台词诱导）。

2.3 多关键词分词打分、rolled_back 剔除与全链路标签清洗 (Bug #49)

提取常量 JOURNAL_VISIBLE_SQL = "COALESCE(status, 'active') NOT IN ('archived', 'rolled_back')" 收口 calendar、expand、_fetch_target_hits 与 _collect_bucket_counts，保留 active 与历史 compressed 日记同时彻底隔离已归档和已回滚测试记录。检索关键词经 _tokenize_search_terms 去重拆分与 _escape_like 转义 \/%/_ 后，由 _build_term_sql_parts 组装参数化 SQL，并依据命中词数、完整短语命中与时间戳排序。将 strip_tool_xml_tags 与 strip_internal_tags 确立为全库唯一清洗权威（SSOT）：compact_service.py（call_llm_for_summary）与 response_pipeline.py（clean_memory_text）统一收口调用 strip_internal_tags，memory_decay.py 与 context_manager.py 复用 strip_tool_xml_tags，统一剥离 <think>、<thought>、<inner_thought>、<monologue>、<property_update> 及 <tool_batch> 等伪 XML 残片。

2.4 四类正交工具路由与无硬限安全探索循环

TOOL_REGISTRY 全部 12 个工具的 description 首词强制前缀为 [Memory]、[Workspace]、[Web]、[Collab] 四大正交标签，[Workspace] 工具明确追加禁止翻找聊天/日记的负向后缀。context_manager.py 在动态尾部协议 get_cross_reference_protocol() 的 <environment_constraints> 内写入 4 行精炼 TOOL ROUTING 对照表（零改动 get_static_system_prompt() 以保全 KV-Cache 静态前缀）。同时移除 MAX_MEMORY_SEARCH_STEPS 硬计数器，将 AgentExecutor(..., max_iterations=None) 默认改为不设人为固定步数限制，由 ToolExecutionEngine._sanitize_tool_output(max_chars=40000) 与前端 stream_controller 承担运行时安全保护。

2.5 前端 Remembering... 跨工具聚合同步

后端 ToolExecutionEngine._format_command_str 显式呈现非默认 target（journals/conversations）与 oldest 排序标识；StreamParser.KNOWN_TOOL_NAMES 全量纳入 4 个工具并支持 XML 降级解析。前端 ChatPanel.jsx 通过 MEMORY_TOOL_NAMES 与 groupConsecutiveMemoryTools 将相邻的任意记忆子工具自动收敛合并为单张 Remembering... 多步卡片，运行态附带呼吸脉冲点，完成态默认折叠并支持展开逐跳查阅 IN / OUT。

后果与架构评估 (Consequences & Evaluation)

架构列装后的正向收益、KV-Cache 兼容性与边界约束

  • ✓ 小模型漏斗导航零偏航：通过四类正交前缀（[Memory]/[Workspace]/[Web]/[Collab]）、[Memory] 工具顺位重构及空范围三级/跨表指引，端侧模型可自主按“日历定界 -> 时间线/分词搜索 -> 详情展开”闭环溯源。
  • ✓ 零污染静态前缀与高信噪比上下文：所有路由说明与记忆指针全部落在 ContextManager.assemble_messages 动态尾部，get_static_system_prompt() 保持字节级不动，KV-Cache 前缀复用不受损；全链路 strip_tool_xml_tags 彻底消除 <tool_batch> 噪声。
  • ✓ 数据库只读安全与回滚状态一致：MemorySearchEngine 全程采用参数化只读查询并严格执行 JOURNAL_VISIBLE_SQL 过滤，防止已撤回 rolled_back 测试日记回流污染问答；单轮输出受 40,000 字符安全截断与流中断控制器保护。
  • ✓ 高内聚可测试深模块：检索、清洗、日历聚合与空日期渐进回退逻辑全部收敛于 MemorySearchEngine 单一深模块内，前端通过 MEMORY_TOOL_NAMES 对四子工具无感聚合同步呈现，后续扩展新记忆源无需改动前后端粘合协议。
